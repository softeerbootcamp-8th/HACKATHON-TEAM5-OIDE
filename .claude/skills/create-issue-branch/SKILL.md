# GitHub 이슈와 연결 브랜치 생성

요청 인자: `$ARGUMENTS`

GitHub 이슈 하나를 만들고 `dev`에서 해당 이슈에 연결된 원격 브랜치를 생성한 뒤 로컬에서 checkout한다. 표준 라벨이 없으면 승인 후 생성하고, 이슈에는 작업 타입과 영역 라벨 및 현재 인증된 사용자를 적용한다. 이슈 구현, 변경사항 commit, `dev` 브랜치 생성은 하지 않는다.

## 필수 입력

호출 인자, 현재 요청과 대화에서 다음 값을 수집한다.

- 작업 타입: `feat`, `fix`, `bug`, `refactor`, `docs`, `test`, `chore` 중 하나
- 영역: `FE`, `BE` 또는 둘 다
- 짧은 이슈 제목
- 배경, 작업 내용, 완료 조건을 작성할 수 있는 맥락

결함을 보고하거나 재현하는 작업에는 `bug`, 알려진 결함을 수정하는 작업에는 `fix`를 사용한다. 필수 값을 파악할 수 없으면 상태를 변경하는 명령을 실행하기 전에 사용자에게 확인한다.

## 이름과 내용 규칙

- 이슈 제목: `<type>: <title>`. 예: `feat: 전역 예외 처리`
- 라벨: 작업 타입 라벨 하나와 영역 라벨 `FE`, `BE` 중 하나 이상을 사용한다.
- 이슈 본문:

  ```markdown
  ## 배경

  <이 작업이 필요한 이유>

  ## 작업 내용

  - [ ] <구체적인 작업>

  ## 완료 조건

  - [ ] <확인 가능한 완료 조건>
  ```

- 브랜치: `<type>/<issue-number>-<english-slug>`. 예: `feat/12-global-exception-handling`

slug는 짧은 영문 소문자 ASCII kebab-case로 작성한다. 한글 제목은 의미를 유지한 간결한 영문 slug로 바꾼다. 이슈 제목과 브랜치 이름에는 `FE`나 `BE`를 포함하지 않는다.

## 표준 라벨과 담당자

다음 라벨을 저장소 표준으로 사용한다. 같은 이름의 라벨이 이미 있으면 색상이나 설명을 덮어쓰지 않고 실제 표기를 사용한다. 없는 라벨만 초안 승인 후 생성한다.

| 라벨 | 색상 | 설명 |
| --- | --- | --- |
| `feat` | `1D76DB` | New feature |
| `fix` | `D73A4A` | Bug fix |
| `bug` | `B60205` | Bug report |
| `refactor` | `5319E7` | Code refactoring |
| `docs` | `0075CA` | Documentation |
| `test` | `FBCA04` | Tests |
| `chore` | `C5DEF5` | Maintenance |
| `FE` | `C2E0C6` | Frontend |
| `BE` | `0E8A16` | Backend |

담당자는 `gh`에 현재 인증된 사용자 한 명을 `@me`로 지정한다. 다른 담당자를 추가하거나 기존 담당자를 제거하지 않는다.

## 사전 점검

이슈를 생성하기 전에 다음 항목을 모두 확인한다.

1. 현재 디렉터리가 Git 저장소인지 확인하고 `git status --short`로 작업 트리를 확인한다.
2. `origin`이 작업 대상 GitHub 저장소를 가리키는지 확인한다.
3. `gh auth status`를 실행한다. 인증이 유효하지 않으면 중단하고 인증 방법을 안내한다.
4. 원격에 `origin/dev`가 있는지 확인한다. 없다면 `main`으로 대체하거나 `dev`를 만들지 않고 중단한다.
5. 저장소 라벨을 조회하고 표준 라벨 중 누락된 항목을 기록한다. 기존 라벨은 대소문자 구분 없이 찾되 실제 GitHub 표기를 사용한다.
6. 영문 slug를 만들고 대표 브랜치 이름을 `git check-ref-format --branch`로 검증한다.

작업 트리에 변경사항이 있으면 변경 경로를 초안에 포함하고, 승인이 해당 변경사항을 새 브랜치로 가져가는 것까지 포함하는지 명시한다. 변경사항을 자동으로 stash, commit, 삭제하지 않는다.

## 초안과 승인

다음 내용을 하나의 초안으로 보여준다.

- 기준 브랜치: `origin/dev`
- 완성된 이슈 제목과 본문
- 작업 타입과 영역 라벨
- 새로 생성할 표준 라벨
- 담당자: 현재 인증된 GitHub 사용자
- 제안한 slug가 포함된 브랜치 패턴
- 작업 트리에 변경사항이 있을 때 해당 경고

사용자의 명시적인 승인을 기다린다. 수정 요청을 받으면 초안을 갱신하고 다시 승인받는다. 승인 전에는 `gh issue create`나 `gh issue develop`을 실행하지 않는다.

## 생성

1. 누락된 표준 라벨을 `gh label create`로 생성한다. 하나라도 실패하면 이슈를 만들지 않는다.
2. 승인된 이슈 본문을 임시 파일에 쓰고 성공과 실패 모두에서 정리되게 한다. 사용자 입력을 셸 구문에 직접 삽입하지 않는다.
3. `gh issue create`에 제목, 작업 타입 라벨, 각 영역 라벨, `--assignee @me`, `--body-file`을 명시적으로 전달해 이슈를 생성한다.
4. `gh issue create`가 반환되면 임시 본문 파일을 삭제한다.
5. 생성에 성공한 뒤 반환된 이슈 URL에서 이슈 번호를 얻는다.
6. 최종 브랜치 이름을 만들고 `git check-ref-format --branch`로 검증한다.
7. 같은 이름의 브랜치가 로컬이나 `origin`에 없는지 확인한다.
8. `gh issue develop <issue-number> --base dev --name <branch-name> --checkout`을 실행한다.

사용자가 별도로 요청하지 않는 한 milestone, project, GitHub issue type을 지정하지 않는다.

## 실패 처리

- 라벨 생성에 실패하면 이슈와 브랜치를 만들지 않는다. 이미 생성된 표준 라벨은 삭제하지 않는다.
- 이슈 생성에 실패하면 브랜치 생성을 시도하지 않는다.
- 이슈 생성 후 브랜치 생성에 실패하면 이슈 URL과 실패 원인을 알린다. 같은 이슈 번호로 브랜치 단계만 재시도하며, 중복 이슈를 만들거나 기존 이슈를 자동으로 삭제하지 않는다.
- 다른 기준 브랜치로 조용히 대체하거나, 요청한 라벨을 생략하거나, 다른 브랜치 이름을 선택하지 않는다.

성공하면 이슈 URL, 적용한 라벨과 담당자, checkout된 브랜치 이름, 기준 브랜치 `origin/dev`를 알린다.
