# Flow 4: 방 생성일 환율 기반 최종 정산 설계

## 1. 목표

Flow 4는 정산방 전체의 `Payment`와 `PaymentShare`를 KRW로 환산해, 참여자별 최종 부담 금액과 송금 목록을 만든다.

그룹은 편집 편의를 위한 단위일 뿐 최종 정산 단위가 아니다. 최종 정산은 방에 속한 모든 결제를 한 번에 계산한다.

## 2. 환율 기준

### 기본 환율

- 환율 기준일은 `SettlementRoom.createdAt`의 `Asia/Seoul` 날짜다.
- 방 생성 시 사용자가 환율을 따로 입력하지 않는다.
- Flow 4 메인 진입 시, 방에 사용된 통화의 자동 환율을 조회해 보여준다.
- 자동 환율은 한국수출입은행 환율 API를 사용한다.
- 해당 날짜에 고시 데이터가 없으면, 방 생성일 이전의 가장 최근 고시일을 최대 10일 전까지 찾는다.
- KRW는 외부 조회 없이 항상 `1 KRW = 1 KRW`로 처리한다.

한국수출입은행 API는 원화 기준 환율과 통화별 고시 단위를 함께 제공하므로, JPY·TWD처럼 100단위로 고시되는 여행 통화를 안전하게 처리할 수 있다.

### 자동 환율 조회와 캐시

자동 환율은 `GET /api/rooms/{roomId}/settlement-preview`에서만 조회한다.

1. 방에 사용된 외화 통화와 방 생성일 기준 최대 10일의 고시일 범위를 확인한다.
2. `ExchangeRate`에서 통화별 가장 최근 고시 환율을 찾는다.
3. 캐시에 없는 통화가 있을 때만 한국수출입은행 API를 호출한다.
4. API 응답의 고시 환율을 정규화해 `ExchangeRate`에 저장한 뒤 미리보기를 계산한다.

`POST /settlement-preview`와 `POST /settlements`는 외부 API를 호출하지 않는다. 두 요청은 캐시된 자동 환율과 요청의 직접 입력 환율만 사용한다. 따라서 사용자가 확인한 미리보기와 확정 결과가 외부 API 재조회로 달라지지 않는다.

방 생성일이 주말이나 휴일이면 캐시와 API 모두에서 해당 날짜 이전의 가장 최근 고시일을 찾는다. 최대 10일 안에 자동 환율을 찾지 못하면 해당 통화는 직접 입력이 필요하다.

한국수출입은행 API 인증 키와 요청 URL은 환경 설정으로 관리하며, 인증 키는 로그나 API 응답에 포함하지 않는다.

### 환율 정규화

모든 환율은 계산과 저장 시 아래 의미로 통일한다.

```text
rateToKrw = 외화 1단위당 KRW
```

API가 반환한 고시 환율은 고시 단위를 나눈다.

```text
rateToKrw = 고시환율 / 고시단위

예: JPY(100) 고시환율이 910.34라면
    1 JPY = 9.1034 KRW
```

## 3. 환율 직접 수정

Flow 4 메인에서 자동 환율을 기본으로 보여주고, 사용자가 `직접 입력하기`를 선택한 통화만 수정할 수 있다.

- 입력 형식: `1 {currency} = {rateToKrw} KRW`
- 입력값은 0보다 커야 한다.
- 수정한 통화는 자동 환율보다 우선한다.
- 자동 환율을 찾지 못한 통화는 `직접 입력 필요` 상태로 표시한다.
- 자동 환율이 없는 통화는 직접 입력하기 전에는 최종 정산을 확정할 수 없다.
- 직접 입력값은 Flow 4 미리보기와 최종 확정 요청에만 전달한다. 방 생성 시점이나 별도 화면에서 미리 저장하지 않는다.

환율 출처는 아래 세 가지로 구분한다.

| source | 의미 |
| --- | --- |
| `EXIM` | 한국수출입은행 자동 환율 |
| `MANUAL` | 사용자가 Flow 4에서 직접 입력한 환율 |
| `FIXED` | KRW의 고정 환율 1 |

## 4. API 설계

### Flow 4 메인 조회

```http
GET /api/rooms/{roomId}/settlement-preview
```

방 생성일 기준 자동 환율과 자동 환율로 계산한 예상 정산 결과를 반환한다. 정산 결과는 저장하지 않지만, 캐시에 없는 자동 환율은 `ExchangeRate`에 저장한다.

### 직접 입력 환율을 반영한 미리보기

```http
POST /api/rooms/{roomId}/settlement-preview
```

```json
{
  "manualRates": [
    {
      "currency": "JPY",
      "rateToKrw": 9.1034
    }
  ]
}
```

자동 환율과 직접 입력 환율을 합쳐 예상 결과를 다시 계산한다. DB에는 저장하지 않는다.

이 요청은 외부 환율 API를 호출하지 않는다. `GET /settlement-preview`에서 저장한 자동 환율을 사용하고, `manualRates`에 포함된 통화만 자동 환율을 대체한다.

### 최종 정산 확정

```http
POST /api/rooms/{roomId}/settlements
```

미리보기와 같은 `manualRates`를 받아 최종 검증, 환율 계산, 정산 결과 저장을 수행한다.

이 요청도 외부 환율 API를 호출하지 않는다. 자동 환율이 캐시에 없고 직접 입력값도 없으면, 해당 통화를 반환하고 정산을 거절한다.

### 저장된 결과 조회

```http
GET /api/rooms/{roomId}/settlements
```

저장된 환율 스냅샷, 참여자별 결과, 송금 목록을 반환한다.

## 5. 최종 정산 전 검증

최종 정산은 아래 조건을 모두 만족할 때만 실행한다.

```text
모든 Payment에 splitGroup이 지정되어 있음
모든 Payment에 splitMethod가 지정되어 있음
모든 Payment에 PaymentShare가 존재함
각 Payment의 PaymentShare 합계가 Payment.amount와 정확히 같음
각 외화 통화에 자동 또는 직접 입력 환율이 존재함
```

하나라도 실패하면 `Settlement`을 만들지 않고, 문제가 있는 결제 ID와 환율이 필요한 통화를 반환한다.

## 6. 원화 환산과 반올림

### 결제 총액 환산

결제 하나의 실제 지출 원화 금액을 먼저 계산한다.

```text
paymentAmountKrw = HALF_UP(payment.amount × rateToKrw)
```

### 분담 금액 환산

각 `PaymentShare`를 독립적으로 반올림하면 분담 합계가 결제 총액과 달라질 수 있다. 따라서 결제 단위로 아래 순서를 지킨다.

1. 각 분담 금액의 정확한 원화 값을 계산한다.
2. 각 값을 원 단위로 내림한다.
3. `paymentAmountKrw - 내림 합계`만큼 남은 원을 계산한다.
4. 소수부가 큰 분담 대상부터 1원씩 배정한다.
5. 소수부가 같으면 `RoomMember.displayOrder`가 빠른 참여자에게 먼저 배정한다.

이 규칙으로 항상 아래 식이 성립한다.

```text
SUM(paymentShareKrw) = paymentAmountKrw
```

## 7. 참여자별 결과와 송금 목록

참여자별로 아래 값을 계산한다.

```text
paidKrw = 자신이 결제한 Payment의 paymentAmountKrw 합계
owedKrw = 자신에게 배정된 paymentShareKrw 합계
netKrw  = paidKrw - owedKrw
```

- `netKrw > 0`: 받을 금액
- `netKrw < 0`: 보낼 금액
- `netKrw = 0`: 송금 없음

송금 목록은 보낼 사람과 받을 사람을 각각 `displayOrder` 순서로 정렬한 뒤, 현재 보낼 금액과 받을 금액 중 작은 값만큼 연결한다.

```text
송금액 = min(보낼 금액, 받을 금액)
```

한쪽의 잔액이 0이 될 때까지 반복하면 총액을 보존하면서 일관된 송금 목록을 만들 수 있다. `displayOrder`를 기준으로 처리하므로 같은 정산 입력은 항상 같은 목록을 반환한다.

### 송금 매칭 예시

참여자별 순액이 아래와 같고, `displayOrder`는 A, B, C, D 순서라고 가정한다.

| 참여자 | netKrw | 상태 |
| --- | ---: | --- |
| A | +7,000원 | 받을 금액 |
| B | +3,000원 | 받을 금액 |
| C | -4,000원 | 보낼 금액 |
| D | -6,000원 | 보낼 금액 |

보내는 사람은 C, D 순서, 받는 사람은 A, B 순서로 처리한다.

| 순서 | 송금 | 송금 후 보낼 잔액 | 송금 후 받을 잔액 |
| --- | --- | ---: | ---: |
| 1 | C → A: 4,000원 | C: 0원 | A: 3,000원 |
| 2 | D → A: 3,000원 | D: 3,000원 | A: 0원 |
| 3 | D → B: 3,000원 | D: 0원 | B: 0원 |

결과 송금 목록은 `C → A: 4,000원`, `D → A: 3,000원`, `D → B: 3,000원`이다. 전체 송금액은 10,000원으로, 받을 금액과 보낼 금액의 총합이 같다.

`netKrw = 0`인 참여자는 송금 목록에서 제외한다. 예를 들어 A가 `+5,000원`, B가 `-5,000원`, C가 `0원`이면 `B → A: 5,000원` 한 건만 생성되고 C는 목록에 나타나지 않는다.

이 규칙은 결정적인 목록을 만드는 규칙이며, 모든 입력에서 송금 건수가 수학적으로 최소임을 보장하는 최적화 알고리즘은 아니다. 현재 요구사항에서는 결과의 재현성과 이해하기 쉬운 정렬 순서를 우선한다.

### 계산 예시

참여자 A와 B가 아래 두 결제를 등록했다고 가정한다.

| 결제 | 결제자 | 금액 | 분담 |
| --- | --- | --- | --- |
| 저녁 식사 | A | USD 15 | A: USD 10, B: USD 5 |
| 교통비 | B | JPY 1,000 | A: JPY 333, B: JPY 667 |

자동 환율은 USD `1,350.25 KRW`, JPY 100단위 고시 `910.34 KRW`라고 가정한다. JPY의 정규화 환율은 `910.34 / 100 = 9.1034 KRW`다.

저녁 식사의 결제 총액과 분담 금액은 아래처럼 계산한다.

```text
결제 총액 = HALF_UP(15 × 1,350.25) = 20,254원

A 분담 정확값 = 10 × 1,350.25 = 13,502.50원 → 13,502원
B 분담 정확값 =  5 × 1,350.25 =  6,751.25원 →  6,751원
내림 합계 = 20,253원, 남은 1원
→ 소수부가 더 큰 A에게 1원 배정

A 분담 = 13,503원
B 분담 =  6,751원
```

교통비는 아래처럼 계산한다.

```text
결제 총액 = HALF_UP(1,000 × 9.1034) = 9,103원

A 분담 정확값 = 333 × 9.1034 = 3,031.4322원 → 3,031원
B 분담 정확값 = 667 × 9.1034 = 6,071.9678원 → 6,071원
내림 합계 = 9,102원, 남은 1원
→ 소수부가 더 큰 B에게 1원 배정

A 분담 = 3,031원
B 분담 = 6,072원
```

최종 참여자별 결과와 송금 목록은 아래와 같다.

| 참여자 | paidKrw | owedKrw | netKrw | 결과 |
| --- | ---: | ---: | ---: | --- |
| A | 20,254원 | 16,534원 | +3,720원 | 받을 금액 3,720원 |
| B | 9,103원 | 12,823원 | -3,720원 | 보낼 금액 3,720원 |

따라서 송금 목록에는 `B → A: 3,720원` 한 건이 생성된다. 각 결제의 분담 금액 합계는 결제 총액과 같고, 전체 `netKrw` 합계도 0이다.

## 8. 저장 모델

방당 `Settlement`은 한 건만 유지한다. 재정산하면 기존 결과를 새 계산 결과로 교체한다.

| 엔티티 | 저장 내용 |
| --- | --- |
| `ExchangeRate` | 자동 환율 캐시: 제공기관, 실제 고시일, 통화, 정규화된 `rateToKrw`, 고시 단위, 조회 시각 |
| `Settlement` | 방, 상태 `COMPLETED`, 계산 시각 |
| `SettlementRate` | 통화, 정규화된 `rateToKrw`, 출처, 고시 기준일, 조회 시각 |
| `SettlementMemberResult` | 참여자별 `paidKrw`, `owedKrw` |
| `SettlementTransfer` | 송금자, 수취자, 송금액 KRW |

필수 제약은 아래와 같다.

```text
UNIQUE (exchange_rate.provider, exchange_rate.announced_date, exchange_rate.currency)
UNIQUE (settlement.room_id)
UNIQUE (settlement_rate.settlement_id, settlement_rate.currency)
UNIQUE (settlement_member_result.settlement_id, settlement_member_result.member_id)
```

`SettlementRate`에는 KRW도 `rateToKrw = 1`, `source = FIXED`로 저장해 최종 결과의 환율 목록을 완전하게 보존한다.

`ExchangeRate`는 여러 방이 재사용하는 자동 환율 캐시이고, `SettlementRate`는 확정 정산에 실제로 사용된 환율 스냅샷이다. 자동 환율 캐시가 이후 갱신돼도 완료된 정산의 `SettlementRate`는 변경하지 않는다. 직접 입력 환율은 미리보기와 확정 요청에서만 전달하며, 확정되기 전에는 어느 테이블에도 저장하지 않는다.

## 9. 트랜잭션과 동시성

최종 확정은 하나의 트랜잭션으로 처리한다.

```text
방 비관적 잠금 조회
→ 결제와 분담 데이터 검증
→ 캐시된 자동 환율과 수동 환율 결정
→ 원화 환산과 참여자별 결과 계산
→ 송금 목록 계산
→ 기존 정산 결과 삭제 또는 교체
→ Settlement, Rate, MemberResult, Transfer 저장
```

중간 단계가 실패하면 전체를 롤백해 일부 결과만 남지 않게 한다.

## 10. 구현 테스트

- 방 생성일 기준으로 USD·JPY·KRW 환율을 조회하고 JPY 100단위 고시를 정규화한다.
- 주말·휴일 방 생성 시 최근 고시일 환율을 찾는다.
- 자동 환율 캐시가 있으면 Flow 4 메인 조회에서 외부 API를 호출하지 않는다.
- 자동 환율 캐시가 없으면 Flow 4 메인 조회에서만 외부 API를 호출하고, 정규화된 결과를 저장한다.
- 미리보기 재계산과 최종 정산 확정은 외부 API를 호출하지 않고 캐시된 환율을 사용한다.
- 직접 입력 환율이 자동 환율보다 우선 적용된다.
- 자동 환율이 없는 통화는 직접 입력 전 확정할 수 없다.
- 결제별 분담 원화 합계가 결제자 원화 지출과 항상 일치한다.
- 그룹 미지정, 분담 방식 미지정, 분담 합계 불일치 결제는 정산을 거절한다.
- 여러 채무자·채권자 조합에서 송금 총액 보존과 `displayOrder` 기반 송금 목록의 재현성을 검증한다.
- 재정산 시 기존 환율·참여자 결과·송금 목록이 남지 않고 교체된다.
- 자동 환율 캐시가 갱신돼도 완료된 정산의 환율 스냅샷과 결과가 변경되지 않는다.
