# OIDE 백엔드 개발 가이드

이 문서는 루트 `CLAUDE.md`를 보충하며 `backend` 아래의 작업에 적용한다.

## 작업 전 확인

- 기능 요구사항은 `PRD.md`를 기준으로 한다.
- 변경할 도메인의 기존 코드와 테스트를 먼저 읽는다.
- 현재 작업에 필요한 최소 범위만 변경한다.
- 작업 트리에 있는 다른 사람의 변경을 수정, 삭제, 스테이징하지 않는다.

## 기술 기준

- Java 21
- Spring Boot 4.1.1
- Spring MVC
- Spring Data JPA
- MySQL
- Gradle Wrapper

새 라이브러리는 표준 라이브러리와 기존 의존성으로 해결할 수 없는 경우에만 추가한다. 의존성 추가와 설정 변경은 현재 요구사항에 직접 필요해야 한다.

## 패키지와 책임

기술 계층보다 도메인을 먼저 나눈다.

```text
com.example.oide
├── room
│   ├── controller
│   ├── service
│   ├── domain
│   ├── repository
│   └── dto
├── payment
├── settlement
└── global
```

- `controller`: HTTP 요청 검증, DTO 변환, 응답 상태 결정
- `service`: 유스케이스 조합과 트랜잭션 경계
- `domain`: 엔티티, 값 객체, 도메인 불변식과 계산
- `repository`: 영속성 조회와 저장
- `dto`: API 요청과 응답 계약
- `global`: 여러 도메인에서 실제로 공유하는 예외와 설정

도메인 하나에서만 사용하는 코드를 `global`로 올리지 않는다. 우연히 비슷한 코드보다 같은 의미로 반복되는 코드만 공통화한다.

## Java 코드 스타일

- 현재 코드의 탭 들여쓰기와 import 그룹 순서를 유지한다.
- 새 포맷터나 포맷 규칙을 임의로 도입하지 않는다.
- 클래스와 변수는 역할이 드러나는 이름을 사용한다.
- 메서드 이름은 동사로 시작하고 반환값이나 변경 동작을 구분한다.
- 불리언은 `is`, `has`, `should`로 시작한다.
- 한 메서드는 한 가지 책임을 가지며 깊은 중첩은 조기 반환으로 줄인다.
- API 요청과 응답처럼 불변인 데이터는 `record`를 우선 고려한다.
- 주석은 코드만으로 알 수 없는 제약이나 설계 이유를 설명할 때만 작성한다.
- 사용하지 않는 코드, 주석 처리한 과거 코드와 미완성 TODO를 남기지 않는다.

## Lombok

- 엔티티에는 필요한 범위의 `@Getter`와 `@NoArgsConstructor(access = PROTECTED)`만 우선 사용한다.
- `@Data`와 전체 필드 setter를 사용하지 않는다.
- `@Builder`는 필수값과 불변식을 우회하지 않는 경우에만 사용한다.
- 단순히 코드를 짧게 만들기 위해 `@EqualsAndHashCode`나 `@ToString`을 엔티티에 추가하지 않는다.

## Spring 규칙

- Controller는 도메인 계산이나 영속성 로직을 수행하지 않는다.
- Service가 트랜잭션 경계를 가진다.
- 조회 전용 Service 메서드는 `@Transactional(readOnly = true)`를 사용한다.
- 생성과 변경은 하나의 명확한 유스케이스 단위로 트랜잭션을 묶는다.
- 내부 호출에서 발생할 수 없는 상황을 습관적인 null 검사나 `try-catch`로 숨기지 않는다.
- 외부 API 실패를 성공 응답이나 빈 결과로 조용히 대체하지 않는다.

## JPA 규칙

- 모든 연관관계는 기본적으로 `FetchType.LAZY`를 사용한다.
- 필요하지 않은 양방향 연관관계를 만들지 않는다.
- API 응답으로 엔티티를 직접 반환하지 않고 DTO로 변환한다.
- 엔티티는 `protected` 기본 생성자와 의미 있는 생성·변경 메서드를 사용한다.
- 엔티티 필드를 직접 변경하는 public setter를 만들지 않는다.
- `CascadeType.ALL`과 `orphanRemoval`은 생명주기 소유 관계가 명확할 때만 사용한다.
- N+1 조회가 예상되면 필요한 fetch join이나 전용 조회 쿼리로 해결한다.
- 데이터 중복을 허용하지 않는 조합은 애플리케이션 검사만으로 끝내지 않고 DB 유니크 제약도 둔다.
- 현재 초기 개발용 `ddl-auto: create` 설정을 요청 없이 변경하지 않는다.
- 데이터를 보존하는 환경으로 전환할 때는 마이그레이션 도구 도입과 `validate` 전환을 별도 작업으로 진행한다.

## 금액과 정산

- 외화 금액과 환율에는 `BigDecimal`을 사용한다.
- 최종 원화 금액은 정수 원 단위로 저장한다.
- 금액 계산에 `double`이나 `float`을 사용하지 않는다.
- 나눗셈의 scale과 `RoundingMode`를 명시한다.
- 원화 환산은 PRD의 원 단위 반올림 정책을 따른다.
- 분담액 합계는 원 결제 금액과 정확히 같아야 한다.
- 결제자와 부담자는 같은 정산방에 속한 참여자여야 한다.
- 정산 결과는 전체 채권과 채무의 합을 보존해야 한다.
- 계산 규칙은 Controller나 DTO가 아니라 도메인 코드에 둔다.

## 요청 검증과 오류 처리

- 사용자 입력, 파일, OCR 결과, 환율 API 응답은 시스템 경계에서 검증한다.
- 내부 타입과 호출 흐름이 보장하는 조건을 반복 검증하지 않는다.
- 예상 가능한 비즈니스 실패는 `BusinessException`과 구체적인 `ErrorCode`로 표현한다.
- Controller마다 중복 `try-catch`를 만들지 않고 `GlobalExceptionHandler`를 사용한다.
- 예외를 삼키거나 임의의 기본값으로 정산 결과를 만들지 않는다.
- 오류 메시지는 원인을 진단할 수 있어야 하지만 내부 구현과 민감 정보를 노출하지 않는다.

## 로깅과 보안

- 비밀번호, 토큰, 개인정보, 결제 원문과 전체 OCR 응답을 로그에 남기지 않는다.
- 요청·응답 전체를 습관적으로 로깅하지 않는다.
- 반복문마다 로그를 기록하지 않는다.
- 예상하지 못한 서버 오류는 `ERROR`, 복구 가능한 외부 연동 문제는 상황에 맞게 `WARN`을 사용한다.
- 사용자 입력을 셸 명령, SQL 또는 HTML에 직접 삽입하지 않는다.
- 비밀값은 환경 변수나 승인된 비밀 저장소에서 주입한다.

## 테스트

- 도메인 계산은 Spring Context 없이 실행되는 단위 테스트를 우선한다.
- Repository와 JPA 매핑은 실제 영속성 경로를 검증한다.
- Controller 테스트는 입력 검증, 상태 코드와 공통 오류 응답을 확인한다.
- 버그 수정은 실패를 재현하는 테스트를 먼저 추가한다.
- 골든 패스를 먼저 확인하고 경계 조건과 실패 경로를 이어서 검증한다.
- mock 호출 횟수만 확인하지 말고 가능한 한 실제 결과와 상태 변화를 검증한다.

백엔드 변경 후 다음 명령을 실행한다.

```bash
./gradlew test
git diff --check
```

테스트 통과만으로 기능이 동작한다고 단정하지 않는다. 변경한 API나 사용자 흐름을 직접 실행해 확인한다.

## 하지 말아야 할 것

- 요청과 관계없는 포맷팅, 리네이밍과 리팩터링을 함께 수행하지 않는다.
- 미래를 위한 인터페이스, 옵션, feature flag와 호환성 shim을 미리 만들지 않는다.
- Entity를 API 계약으로 노출하지 않는다.
- `EAGER` 로딩을 기본값으로 사용하지 않는다.
- 무분별한 setter, `@Data`, `CascadeType.ALL`을 사용하지 않는다.
- 금액을 부동소수점으로 계산하거나 반올림 정책을 암묵적으로 두지 않는다.
- 광범위한 예외를 잡아서 무시하거나 정상 흐름으로 바꾸지 않는다.
- 비밀 정보와 개인정보를 코드, 설정 기본값 또는 로그에 하드코딩하지 않는다.
- 테스트 실패를 숨기거나 실행하지 않은 검증을 통과했다고 기록하지 않는다.
- 명시적인 요청 없이 commit, push, merge, force push 또는 브랜치 삭제를 하지 않는다.

## 완료 전 점검

- 변경이 PRD와 요청 범위에 맞는가.
- 도메인 불변식이 코드와 DB 제약으로 필요한 만큼 보호되는가.
- API에서 엔티티가 직접 노출되지 않는가.
- 금액 단위, 통화 코드와 반올림 방식이 명확한가.
- 예외와 외부 연동 실패 경로를 확인했는가.
- 사용하지 않는 import, 임시 로그와 미완성 코드가 없는가.
- 변경 범위에 맞는 테스트와 실제 실행 확인을 완료했는가.
