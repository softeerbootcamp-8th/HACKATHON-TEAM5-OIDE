# GitHub PR 등록

현재 브랜치의 작업을 `dev` 대상으로 PR 하나만 등록한다. 작업 타입과 연결 이슈의 영역 라벨 및 현재 인증된 사용자를 PR에 적용한다. 소스 수정, 자동 commit, 강제 push, merge, reviewer·milestone·project 지정은 하지 않는다.

## 연결 이슈

현재 브랜치 이름은 `<type>/<issue-number>-<slug>` 형식이어야 한다. 허용하는 타입은 `feat`, `fix`, `bug`, `refactor`, `docs`, `test`, `chore`다.

브랜치 이름에서 이슈 번호를 추출한다. 사용자가 이슈 번호를 지정했다면 브랜치의 번호와 같은지 확인한다. 번호가 없거나 서로 다르면 PR을 만들지 않고 중단한다.

이슈와 PR은 다음 규칙으로 1:1 연결한다.

- 이슈가 `OPEN` 상태여야 한다.
- 현재 브랜치가 `gh issue develop`로 해당 이슈에 연결된 브랜치여야 한다.
- 현재 브랜치에 기존 PR이 없어야 한다.
- 해당 이슈를 종료 대상으로 참조하는 다른 PR이 없어야 한다.
- 새 PR 본문에는 `Closes #<issue-number>`를 정확히 한 번만 넣는다.

## 라벨과 담당자

- 작업 타입 라벨은 브랜치의 `<type>`과 같은 이름을 사용한다.
- 영역 라벨은 연결 이슈에 붙은 `FE`, `BE`를 그대로 사용한다. 영역 라벨이 없으면 PR을 만들지 않는다.
- 표준 라벨은 다음 정의를 사용한다.

  | 라벨 | 색상 | 설명 |
  | --- | --- | --- |
  | `feat` | `1D76DB` | New feature |
  | `fix` | `D73A4A` | Bug fix |
  | `bug` | `B60205` | Bug report |
  | `refactor` | `5319E7` | Code refactoring |
  | `docs` | `0075CA` | Documentation |
  | `test` | `FBCA04` | Tests |
  | `chore` | `C5DEF5` | Maintenance |
  | `FE` | `C2E0C6` | Frontend |
  | `BE` | `0E8A16` | Backend |

- 누락된 표준 라벨은 초안 승인 후 생성한다. 기존 라벨의 색상이나 설명은 덮어쓰지 않는다.
- 담당자는 `gh`에 현재 인증된 사용자 한 명을 `@me`로 지정한다. 다른 담당자를 추가하거나 기존 담당자를 제거하지 않는다.

## 사전 점검

상태를 변경하기 전에 다음 항목을 모두 확인한다.

1. `gh auth status`로 GitHub 인증을 확인한다.
2. `origin`이 작업 대상 GitHub 저장소를 가리키는지 확인한다.
3. 현재 브랜치가 `main`이나 `dev`가 아니며 브랜치 이름 규칙을 만족하는지 확인한다.
4. `origin/dev`가 존재하는지 확인하고 원격 상태를 갱신한다.
5. 작업 트리가 깨끗한지 확인한다. commit되지 않은 변경사항이 있으면 중단하고 commit이 필요하다고 알린다. 직접 commit하지 않는다.
6. `gh issue view`로 연결 이슈의 번호, 제목, 상태, URL, 종료 대상 PR 참조를 확인한다.
7. `gh issue develop --list`로 현재 브랜치가 연결 이슈의 개발 브랜치인지 확인한다.
8. `gh pr list --head <current-branch> --state all`로 현재 브랜치의 기존 PR을 확인한다.
9. `origin/dev...HEAD`에 PR로 올릴 commit과 diff가 실제로 존재하는지 확인한다.
10. 로컬과 원격 작업 브랜치의 앞섬·뒤처짐을 확인한다. 원격과 갈라졌거나 로컬이 뒤처졌으면 중단하며 rebase, merge, force push를 자동 실행하지 않는다.
11. 저장소와 연결 이슈의 라벨을 조회해 적용할 작업 타입·영역 라벨과 새로 생성할 표준 라벨을 확정한다.

종료 대상 PR 참조가 있거나 현재 브랜치의 기존 PR이 있으면 새 PR을 만들지 말고 해당 PR URL을 알린다.

## 변경 분석과 검증

- `git log origin/dev..HEAD`와 `git diff origin/dev...HEAD`를 읽어 실제 변경사항만 요약한다.
- 저장소의 빌드 설정과 기존 테스트 관례를 확인하고 변경 범위에 맞는 테스트 또는 검증 명령을 실행한다.
- 실행하지 않은 테스트를 통과했다고 쓰지 않는다.
- 검증이 실패하면 결과를 알리고 PR 생성을 계속할지 사용자에게 확인한다. 실패를 숨기거나 코드를 수정하지 않는다.

PR 제목은 연결 이슈 제목과 동일하게 사용한다. PR 본문은 `.github/pull_request_template.md`의 구조를 유지하면서 안내 문구를 실제 내용으로 교체한다.

```markdown
## 🔗 연결 이슈

Closes #<issue-number>

## 📝 작업 요약

- <구현한 작업>
- <필요한 이유와 해결한 문제>

## 🛠 주요 해결 과정

- <해결 방법>
- <중요한 구현 흐름과 설계 결정>
- <실제로 실행한 테스트와 확인 결과>
```

다른 이슈 번호가 필요하면 종료 키워드 없이 일반 텍스트로 언급한다. `Closes`, `Fixes`, `Resolves` 같은 종료 키워드는 연결 이슈 하나에만 사용한다.

## 초안과 승인

다음 내용을 하나의 초안으로 보여주고 명시적인 승인을 기다린다.

- 연결 이슈 번호와 URL
- base: `dev`
- head: 현재 브랜치
- 이슈 제목과 동일한 PR 제목
- 완성된 PR 본문
- 실행한 테스트와 결과
- push할 commit 수
- 적용할 작업 타입·영역 라벨과 새로 생성할 표준 라벨
- 담당자: 현재 인증된 GitHub 사용자

수정 요청을 받으면 초안을 갱신하고 다시 승인받는다. 승인 전에는 push하거나 `gh pr create`를 실행하지 않는다.

## 등록

1. 누락된 표준 라벨을 생성한다. 하나라도 실패하면 push와 PR 생성을 하지 않는다.
2. 로컬 commit이 원격 작업 브랜치보다 앞서 있으면 현재 브랜치를 `origin`에 일반 push한다. force push는 하지 않는다.
3. 승인된 PR 본문을 임시 파일에 쓰고 성공과 실패 모두에서 정리되게 한다. 사용자 입력을 셸 구문에 직접 삽입하지 않는다.
4. `gh pr create --base dev --head <current-branch> --title <issue-title> --body-file <file>`로 일반 PR을 생성한다. draft로 만들지 않는다.
5. 명령이 반환되면 임시 본문 파일을 삭제한다.
6. 생성된 PR에 작업 타입·영역 라벨과 `--assignee @me`를 적용한다.
7. `gh pr view`로 base, head, 본문, 라벨, 담당자, `closingIssuesReferences`를 다시 조회한다.
8. 적용한 라벨과 담당자를 검증하고, 종료 대상 이슈가 정확히 하나이며 처음 확인한 이슈 번호와 같은지 검증한다.

push 후 PR 생성이 실패하면 push된 브랜치와 실패 원인을 알리고 같은 head 브랜치로 PR 생성 단계만 재시도한다. PR이 생성된 뒤 검증에 실패하면 해당 PR URL과 불일치를 알리고 두 번째 PR을 만들지 않는다.

PR 생성 후 라벨이나 담당자 적용에 실패하면 생성된 PR URL과 실패한 메타데이터를 알린다. 같은 PR에 메타데이터 적용만 재시도하며 두 번째 PR을 만들지 않는다.

성공하면 PR URL, 연결 이슈, base와 head, 적용한 라벨과 담당자, 테스트 결과를 간결하게 알린다.
